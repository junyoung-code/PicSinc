실제 B 5팀 1회(2026-09-26, 공개 앱, `주녕1`~`주녕5`): 사용자가 스톱워치로 마지막 원본 YOLO 완료까지 약 1분 30초, 방 생성·병합은 짧았다고 보고했다. 기록 시작을 누르지 않아 Mac 화면의 대기열·구간 기록은 없다. 운영 DB 작업 시각을 읽기 전용으로 대조한 결과, 첫 업로드 준비부터 마지막 YOLO 완료까지 1분 32초, 각 원본 작업 접수→완료 23·38·52·67·81초였다. 원본 5건과 병합 5건 모두 `ready`, 각 1회 시도였다. 병합 작업 접수→완료는 약 10·15·20·26·31초였다. 이 시간에는 작업 대기가 포함되며 워커 처리 시간과 분리할 수 없다.

실제 B 10팀 1회(같은 날, 공개 앱, `주녕1`~`주녕10`): 사용자는 진행상 문제가 없었다고 재확인했다. 당시 3명은 병합까지 진행하지 않았고 화면에 ‘다른 사진을 처리하고 있어요’가 위·아래 두 곳에 표시됐다는 기록이 있다. 이 문구를 시험 실패나 중단 원인으로 확정할 근거는 없다. 운영 DB에는 원본·YOLO 10건 모두 `ready`(각 1회 시도), 얼굴 영역 마스크 10팀 저장, 보정본·병합 결과 7팀 저장이 남았다. `주녕1`~`주녕3`은 마스크 이후 보정본·병합 기록이 없다. 첫 업로드 준비→마지막 YOLO 완료는 2분 57초. 7건의 병합 작업은 모두 `ready`(각 1회 시도)이고, 첫 병합 접수→마지막 완료는 51초, 개별 접수→완료는 약 11~43초다. 화면의 동일 문구 두 곳은 하나의 오류를 부모·편집기에서 각각 표시하는 코드 경로가 있으며 실제 HTTP 429 횟수는 DB만으로 확정할 수 없다. Mac 측정 화면은 `BTEST` 접두어로 시작돼 실제 한글 이름을 집계하지 못했다. 정확한 대기·워커 구간·비용 수치는 없다.

동일 사진 영향: 5팀은 서로 다른 방·원본 자산·YOLO 작업 각 5개, 10팀은 각 10개가 생성돼 모두 실행됐다. 중복 제거는 파일 내용이 아닌 방의 자산 ID·버전에 적용되고, YOLO는 작업마다 별도 프로세스에서 실행된다. 따라서 같은 사진 때문에 분석 작업이 생략되거나 결과가 공유되지는 않았다. 다만 같은 파일 크기와 장면 조건만 시험했으므로 다양한 사진에서 걸리는 시간까지 대표하지는 않는다.

사용량 기준: 운영 DB 21,499,027바이트, Storage 객체 7개·17,690,261바이트다. 9월 25일 조직 전체 사용량은 Supabase egress 0.805/5GB·Storage 평균 0.031/1GB, Vercel 최근 30일 함수 호출 41,084/1,000,000·Fast Data Transfer 260.65MB/100GB·Active CPU 34분 26초/4시간이다. PicSync만의 사용량이 아니며 대시보드 갱신 지연이 있다.

로컬 B 검사: 전체 104개 중 101개 통과·외부 통합 3개 설정 미실행, 타입 검사·프로덕션 빌드 통과. Mac 측정 화면의 기록 시작·조회·종료를 시험 접두어로 확인했다. 실제 5·10팀 시험은 위에 기록했고 워커 중단 복구·비용 추산은 미실행이다.

## C·D. 집 PC 워커 운영·증설

- [△] Windows GTX 1060 3GB 상시 워커용 코드를 `main`에 반영하고 자동 배포했다. 명시적 CUDA 선택·GPU 실패 시 접수 중지, Windows 실행 경로·시작 스크립트·GPU 사전 점검, 인증된 대기열 상태 조회를 추가했다. 상태 조회 API가 포함된 운영 배포는 Ready이지만 Windows 실기·장시간 검증은 별도로 남았다.
- [△] 화질 비교: 비공개 기준 사진 4장의 Mac 결과는 `private/quality/`에 보관했고, 사용자 보고에 따르면 Windows 결과도 같았다. 운영 서버에 올린 별도 2880×3600 사진은 Windows가 34개 영역을 검출했고, 같은 원본을 Mac MPS에서 재분석한 결과도 34개였다. 각 대응 마스크의 최저 IoU는 0.9999로, 이 사진의 어색한 윤곽은 플랫폼 차이가 아니라 공통 YOLO·겹침 처리 결과다. 합성 PNG의 Windows 실측 결과 기록은 별도로 확인해야 한다.
- [△] Windows 실제 검증: 운영 서버의 첫 검출 작업은 유지 신호 중단 후 `worker_lost`로 실패했고, 다음 검출 작업은 1회 시도로 완료됐다. 중단 원인·재부팅 복구, 5·10팀 단독 부하, 4시간 연속 운전이 남았다. 통과 전에는 Windows로 주력 워커를 전환하지 않는다. Mac 동시 실행 시험은 후속이다. 절차는 [Windows 워커 안내](deploy/windows-worker.md)를 따른다.
- 2026-09-27 연결 확인: Mac 워커 서비스·프로세스가 꺼진 상태에서 공개 서버에 128×128 합성 사진 검출 작업을 넣어 12.74초 만에 `ready` 완료를 확인했다. 시험 후 대기·진행 작업은 0건이다. 다른 원격 워커가 없다면 Windows 워커가 처리한 것으로 판단된다. 이 시험은 실제 사진 처리 시간·CUDA 사용·`m` 모델 로드·장시간 안정성을 검증하지 않는다. 이후 상태 조회 API를 배포했으나 Windows 실행 프로세스는 아직 직접 확인하지 않았다.
- [△] Telegram `/status`와 대기 증가·정상화·실패·조회 장애 알림 코드를 `9253601`로 `main`에 push했다. 사용자는 전용 봇을 만들고 Windows에서 연결해 작동한다고 보고했다. Mac의 가짜 Telegram·워커 API 연동 테스트를 포함한 알림 테스트 6개, 전체 Node 테스트 121개 통과·외부 연동 3개 미실행, 타입 검사를 확인했다. 운영자가 `/status` 실제 응답 문구를 공유하지 않아 내용은 직접 대조하지 않았고, 대기 증가 조건의 실제 알림 수신과 Windows 재부팅 후 감시 자동 시작은 남았다. Windows PC 자체의 전원 단절 알림에는 독립된 외부 감시가 필요하다. 운영 절차는 [운영 안내](deploy/dual-worker-monitoring.md)에 있다.
- [✓] 2026-09-27 두 워커 동시 시험: 두 방의 분석과 합성이 모두 `ready`, 시도 1회로 끝났다.
