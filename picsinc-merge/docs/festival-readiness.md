# PicSync 축제 운영 검토

작성: 2026-09-25. 축제 운영을 위한 논의한 문제와 대응 후보를 모은 검토 자료이며, 아래 대응안은 구현 확정 사항이 아니다.
제품 동작은 [MASTER_SPEC](../MASTER_SPEC.md), 실제 진행·검증 상태와 미정 사항은 [STATE](../STATE.md), 실행 방법은 [배포 안내](../deploy/README.md)를 기준으로 한다.

## 1. 문제별 범주와 대응 후보

### A. 보안·개인정보

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| 다른 방·참여자의 사진과 수정 권한 접근 | 사진 유출·무단 편집·삭제 | API마다 방 참여·파일 소속·소유권·대표자 권한을 검증하는지 재확인 |
| 초대 링크·참여증·복구 정보 유출 | 의도하지 않은 참여나 작업 권한 탈취 | 초대 링크로 허용되는 범위 설명, 비밀값 로그 제외, 공용 기기 종료 절차 |
| 방 생성·업로드·분석 요청 남발 | 저장소·처리 자원 고갈, 비용 증가 | 참여자·방·IP별 요청 제한과 전체 접수 상한 검토. 학교 공유 IP만으로 과도하게 차단하지 않기 |
| 거대하거나 잘못된 이미지 | 디코딩 중 메모리 부족·처리 실패 | 기존 파일 크기·픽셀·형식 검증을 실제 경계값과 위장 파일로 확인 |
| 사진·임시 파일·로그 잔존 | 보관 기간 이후 개인정보 노출 | 기존 만료·삭제 규칙 검증, 워커 임시 파일·오류 로그와 늦은 업로드까지 점검 |
| 처리·보관 안내 부족 | 사용자가 사진의 저장·처리 범위를 모름 | 사진 업로드 전 안내와 동의 흐름 검토. 현재 제품에 없는 외부 보정 API를 사용한다고 안내하지 않기 |
| 워커 인증값 유출·개인 PC 침해 | 작업 사진 접근과 처리 서비스 악용 | 별도 작업 계정, 최소 권한, 비밀값 보호·교체 절차, 개인 파일 접근 범위 축소 |

### B. 서버 부하·대기열·비용

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| 촬영·접속·보정·제출 시점이 팀마다 다름 | 촬영 속도로 순간 요청량을 예측하기 어렵고, 나중에 여러 팀의 제출이 겹칠 수 있음 | 즉시 이용·원본만 등록 후 복귀·나중에 이용하는 흐름을 구분해 관찰하고 몰아서 제출하는 상황 시험 |
| 사진 작업이 처리 속도보다 빠르게 유입 | 대기 시간이 계속 늘어남 | 처리 동시 수 제한, 대기 시간·개수 관찰, 과부하 시 접수 제한·안내 |
| 상태 조회·새로고침 집중 | 사진 처리와 별개로 API·DB 부하 증가 | 실제 조회 빈도와 요청량 측정, 비활성 화면 조회 중단·실패 시 간격 증가 검토 |
| 중복 클릭·연결 끊김 후 재시도 | 같은 작업 반복·비용 증가 | 기존 중복 방지와 결과 재사용 확인, 무한 재시도 방지 |
| 큰 PNG·여러 보정본·마스크 | 업로드 지연·저장량·다운로드 전송량 증가 | 팀당 파일 수와 총 바이트 측정, 다운로드 횟수 포함 비용 계산 |
| 서비스 요금제의 자원·사용량 한도 | 오류·서비스 제한·예상 밖 비용 | 행사 전 실제 Vercel·Supabase 요금제와 한도 확인, 예산 알림·대응 기준 결정 |
| 워커 중단 후 작업 재할당 | 중복 실행·오래된 결과 게시 위험 | 할당 만료·복구·오래된 완료 거절을 장애 시험으로 확인 |

### C·D. 집 PC 워커 운영·증설

Windows GTX 1060 3GB PC를 상시 워커로 준비하고, 대기열이 밀리거나 문제가 생기면 기존 Mac 워커를 수동으로 켠다. 기존 대기열 배정 기능을 사용하므로 새 분배 코드는 필요 없다. 실행·화질 검증 절차는 [Windows 워커 안내](../deploy/windows-worker.md)를 따른다.

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| 잠자기·로그아웃·재부팅·업데이트 | 웹은 열려도 사진 처리가 멈춤 | 행사 시간 전원·로그인 유지, 재시작 뒤 자동 실행과 실제 처리 확인 |
| 정전·공유기 장애·인터넷 단절 | 작업 중단·전송 실패·대기 누적 | 복구 절차와 대체 처리 수단 준비. 같은 집 두 대는 공통 장애를 공유함 |
| 발열·먼지·냉각 부족·장시간 부하 | 속도 저하·종료·하드웨어 부담 | 환기·냉각 상태 확인, 장시간 연속 처리 시험, 온도·메모리 관찰 |
| 전기 사용·소음·생활 프로그램 경쟁 | 운영 부담·처리 속도 변동 | 소비전력 측정, 행사 중 무거운 개인 작업 제한 |
| 개인 PC에서 업로드 파일 처리 | 취약한 이미지 처리기 등을 통한 침해 위험 | 런타임 보안 업데이트, 최소 권한 실행, 임시 작업 폴더 분리 |
| 집 회선 업로드 속도·디스크 부족 | 결과 반환 지연·작업 실패 | 실제 전송 속도와 여유 공간 확인, 임시 파일·로그 정리 |

현재의 작업 가져오기 방식과 실행 방법은 [배포 안내](../deploy/README.md)를 따른다. 외부 포트 개방이 필요 없는 구조라도 사진 처리·인증값 취급 위험은 별도로 관리한다.

#### GTX 1060 PC 검증

상시 운영 전 GPU 사용·화질·복구를 확인한다. Mac 동시 처리 시험은 후속 단계다.

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| VRAM 용량·OS·드라이버·실행 환경 차이 | 실행 불가·GPU 대신 CPU 처리·메모리 부족 | 3GB/6GB 모델과 OS 확인, 호환되는 추론 환경에서 실제 GPU 사용 검증 |
| Mac 대비 성능을 모름 | 추가 PC를 켜도 기대만큼 개선되지 않음 | 같은 사진 묶음으로 전체 작업 시간을 비교. GPU 이름만으로 속도 단정하지 않기 |
| 여러 작업 동시 실행 | VRAM 부족·실패·속도 저하 | 우선 한 번에 한 작업으로 측정한 뒤 동시 수 결정 |
| 분석 외 병목 | GPU 추가 후에도 합성·DB·전송 지연 | YOLO 분석과 CPU 합성·전송을 분리 측정 |
| 다중 워커 간 작업 경쟁 | 중복 처리·오래된 결과·특정 PC에 작업 집중 | 두 워커 동시 할당·중단·재할당 검증, 워커 구별·인증값 관리 방식 검토 |
| 설치·업데이트·오류 대응 증가 | 행사 중 운영 복잡성 증가 | 동일 모델·처리 기준 유지, 자동 시작·로그·재시작 절차 준비 |
| 같은 집에서 함께 실행 | 전원·회선 장애에 동시에 멈춤 | 처리량 추가와 장애 대비를 구분해 주력·보조·예비 역할 결정 |

### E. 포토부스·모바일 사용 흐름·사진 품질

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| 촬영 원본 전달이 어렵거나 늦음 | PicSync를 시작하지 못함 | 부스의 디지털 원본·QR 다운로드 제공과 실제 전달 시간 확인 |
| 원본이 메신저에서 압축됨 | 최종 화질 저하 | 팀원에게 동일 원본을 전달하는 방법 안내 |
| 외부 보정 앱이 자르기·회전·크기·얼굴 위치를 바꿈 | 합성 위치·윤곽 불일치 | 지원 조건에 맞는 앱 설정 안내, 실제 보정 사진으로 확인 |
| 머리카락·턱선·붙어 있는 얼굴·겹침 | 이중 윤곽·색 차이·부자연스러운 결과 | 대표 사진으로 경계 품질 확인, 수동 수정 안내와 결과 한계 설명 |
| 한 명이 미제출·중도 이탈 | 팀 전체가 불필요하게 기다림 | 기존 부분 병합 규칙을 사용자가 이해하는지 확인. 제품 규칙은 MASTER_SPEC 참조 |
| 와이파이 혼잡·모바일 통신 불안정 | 업로드 실패·중복 시도 | 느린 네트워크·중간 끊김·재접속 시험 |
| QR 인앱 브라우저와 외부 앱 왕복 | 다른 브라우저로 복귀해 참여 상태 혼동 | 실제 iPhone·Android에서 시작부터 복귀·저장·공유까지 시험 |
| 미저장 초안·동시 저장·대표자 삭제 | 작업 유실 체감·버전 충돌·갑작스러운 종료 | 기존 초안·충돌·삭제 안내와 복귀 동작 확인 |
| 공용 기기에 이전 팀 상태가 남음 | 다른 팀 사진 노출·잘못된 방 참여 | 팀 교체 시 브라우저 상태 정리와 개인 휴대폰 사용 동선 마련 |

### F. 현장 운영·장애 대응

| 문제 | 발생 가능한 영향 | 검토할 대응·확인 |
|---|---|---|
| 사이트만 열어 보고 정상이라고 판단 | 워커 중단을 늦게 발견 | 마지막 워커 응답·대기 시간·실패율·저장 공간·사용량을 운영자에게 알림 |
| 처리 시간을 확정적으로 안내 | 긴 대기 시 사용자 불신 | 실측 대기 기준과 혼잡 안내, 실패·수동 선택 등 가능한 다음 행동 표시 |
| 문제 발생 시 담당자·조치가 불명확 | 현장 대응 지연 | 담당자, 워커 재시작, 접수 일시 중지, 사용자 안내 순서 준비 |
| 행사 직전 변경·환경 불일치 | 새 장애·복구 지연 | 최종 리허설 후 변경 최소화, 배포·워커 버전 확인 및 복구 절차 준비 |

### G. PicSync 이름 통일

표시명과 운영 식별자를 나눠 점검한다. 이름 변경의 진행 상태는 STATE에서 관리한다.

| 범위 | 확인할 항목 | 주의할 점 |
|---|---|---|
| 사용자에게 보이는 이름 | 화면·페이지 제목·공유 미리보기·안내·홍보물 | PicSync 표기 통일 |
| 배포 주소·QR | 공개 도메인·초대 링크·인쇄 QR | 주소 변경 시 기존 링크를 유지하거나 연결할 방법 필요 |
| 코드·문서 | 패키지명·문서·설정 참조 | 일괄 문자열 변경보다 참조 관계 확인 |
| PC 실행 환경 | 자동 실행 이름·설치 경로·로그 경로·워커 URL | 경로 변경 후 재설치·중복 실행 방지·처리 확인 |
| 외부 프로젝트 식별자 | 배포·DB 프로젝트명 | 표시명 통일을 위해 모든 내부 ID를 바꿀 필요는 없음 |

## 2. 다음 논의 순서

1. 부스 수·촬영 주기·원본 전달 방법·운영 시간을 확인한다.
2. 촬영 후 접속·원본 등록·외부 보정·복귀·제출까지의 흐름과 실제 작업 요청 시점을 리허설로 확인한다.
3. 같은 사진으로 Mac과 GTX 1060 PC의 분석·합성·전송 시간을 비교한다.
4. 지연 접속·동시 제출·연결 끊김·워커 중단·재시작을 포함한 부하·복구 시험을 설계한다.
5. 측정값으로 동시 처리 수·접수 상한·알림·예산·현장 대응 기준을 정한다.
6. PicSync 표시와 주소·QR·자동 실행 경로의 변경 범위를 정한다.

우선 검토 순위는 사진 접근 권한·삭제·원본 전달·실기기 왕복·처리량 측정·장애 알림이다. GPU 증설 규모는 측정 후 판단한다. 이는 제안 순서이며 완료 목록이 아니다.
