# ① 공유 작업과 사진 보관

## 역할

사람들이 같은 작업에 참여하고, 자신의 사진과 편집 내용을 저장하고 다시 열 수 있게 합니다.

## 핵심 구현

- 작업 생성과 공유 링크, 닉네임 참여 화면을 만듭니다.
- 브라우저 자동 인식과 개인 복구 링크로 자신의 작업을 이어가게 합니다.
- 원본 업로드·다운로드, 참여자별 보정본 업로드를 구현합니다.
- ②가 전달한 개인 선택 영역과 공동 겹침 수정 내용을 저장·조회합니다. 원본·보정본과 ③의 결과 파일을 보관합니다.
- 서버 저장 요청에 참여자 권한과 작업 버전을 연결하고, ④에서 전체 흐름을 검증합니다.
- 작업의 24시간 만료를 검사하고, 만료된 파일·DB 정보를 삭제하는 함수를 만듭니다. 주기 실행 연결은 ④가 담당합니다.

## 연결 범위

참여·권한의 제품 기준은 [요구사항](../../MASTER_SPEC.md)을 따릅니다. 영역을 그리는 화면은 [②](task-2-editor.md), 사진 합성은 [③](task-3-composition.md)이 담당합니다. 별도 계정 로그인 기능은 만들지 않습니다.

## 완료 기준

- 두 참여자가 같은 작업에서 각자 보정본을 업로드하고 선택 영역을 저장·조회합니다.
- 같은 브라우저 재접속과 다른 브라우저의 개인 복구 링크 사용으로 자기 작업을 이어갑니다.
- 같은 닉네임을 써도 참여자가 구분되고, 다른 사람의 개별 작업은 덮어쓸 수 없습니다.
- 만료된 작업에는 접근할 수 없고, 삭제 함수를 실행하면 파일과 편집 정보가 정리됩니다.

진행 상황은 [STATE.md](../../STATE.md)에서만 관리합니다.

## 직접 업로드 연결

- `direct-uploads-service.ts`는 파일 등록 전 크기·실제 형식·원본 치수·마스크를 검증하고, 등록 완료 요청을 반복해도 같은 방·파일을 반환합니다. 복구 링크로 교체된 참여증을 이전 업로드 완료 요청이 되살리지 못하도록 검사합니다.
- `direct-uploads.ts`의 HTTP 함수는 원본 준비, 방의 보정본·마스크 준비, 완료 요청을 담당합니다. 새 방 화면은 공통 `uploadOriginal`을 사용합니다. 원본 분석 접수는 방 등록과 같은 DB 트랜잭션의 트리거가 담당합니다.
- `storage/direct-uploads.sql`은 메인 검토·마이그레이션용 초안입니다. 업로드 기록에 원문 비밀 토큰을 저장하지 않으며, 임시 파일과 실패한 확정 파일의 정리는 기존 주기 정리에 연결합니다.
- 집중 검증: `node --import tsx --test src/features/photo-session/direct-uploads.test.ts`. 완료 응답 유실·재전송, 다른 브라우저/참여자의 완료 거절, 복구 이후 재전송, 실제 파일 검증, 만료, 크기를 알 수 없는 스트림의 용량 제한을 다룹니다.


## 모바일 흐름 연결

- `service.ts`·`types.ts`: 원본 선택과 공유 검출 캐시, 제출 상태, 대표자 병합·겹침 권한을 연결합니다. 화면은 보정본 업로드 후 스냅샷을 다시 받아 새 버전을 사용합니다.
- `image-validation.ts`: JPEG·PNG의 MIME·실제 디코딩, 20MB·4천만 픽셀 상한과 원본 크기를 검사합니다. 선택 저장 시 실제 마스크의 크기와 선택 픽셀도 확인합니다.
- `supabase-photo-session-store.ts`·`mobile-flow.sql`: 참여·업로드·선택 저장과 버전 변경을 같은 트랜잭션에서 처리합니다. SQL은 메인 검토·적용용 초안이며 기존 활성 방이 있으면 전환을 거부합니다.
- `original-selection` API는 원본 선택을 저장하고 기존 `selection` API는 제출을 처리합니다. 원본 검출 API는 모든 참여자가 첫 저장 결과를 공유합니다.
- 집중 검증: `node --import tsx --test src/features/photo-session/service.test.ts`. 권한, 한 명 이상 제출 후 부분 병합, 미제출자의 이전 선택 제외, 재접속, 빈 선택, 저장 충돌, 병합 중 늦은 참여, 검출 캐시 경쟁, 파일 검증을 다룹니다. 실제 DB 적용·원격 검증과 진행 기록은 메인이 담당합니다.

## 원본 검출 진단 (2026-09-22)

- 변경 파일: `service.ts`·`types.ts`·`service.test.ts`·`detect-regions.ts`·`supabase-photo-session-store.ts`. 요청 ID별로 권한 확인, 파일 조회, 캐시 조회, 사진 다운로드, YOLO 실행, 재인증, 캐시 저장의 시작·성공·실패와 소요 시간을 서버 콘솔에 남깁니다.
- Supabase 캐시 RPC 실패 시 HTTP 상태와 오류 코드·메시지·세부 내용을 길이 제한해 남깁니다. YOLO 내부 실패도 원래 오류를 길이 제한해 남긴 뒤 기존 503 응답을 유지합니다. 사진·마스크 본문과 초대/참여 토큰은 기록하지 않습니다.
- 테스트: 캐시 실패 단계와 요청 ID, 인증 정보 비노출을 `service.test.ts`에서 확인했습니다. 전체 테스트 47개 통과·원격 HTTP 1개 기본 제외, 타입 검사 통과. 실제 사용자 사진의 재시도와 정확한 원인 판별은 로컬 수동 테스트를 기다립니다.
