# 축제 B: 대기 시간 시험 5가지

진행 상태는 [STATE](../STATE.md), 제품 동작은 [MASTER_SPEC](../MASTER_SPEC.md)를 따른다. 아래는 브라우저에서 한 가지씩 재현할 시험이다. 실제 처리량과 비용은 측정 전까지 확정하지 않는다.

## 공통 준비

- 같은 크기·형식의 시험 사진을 준비한다. 팀은 각각 **별도 방**으로 만들고, 한 방의 서로 다른 참여자는 별도 브라우저 프로필이나 기기를 쓴다. 로그인 계정은 필요 없다.
- 먼저 1팀으로 동작을 확인하고, 5팀, 10팀 순서로 늘린다. 같은 사진 조건과 워커 1대 조건을 유지한다.
- 각 시험에서 화면의 시작·완료 시각과 오류를 적는다. ①의 측정 화면을 쓰고, 나머지 시험은 아래 **측정 준비와 기록**을 참고한다.
- 시험 환경과 공개 서비스에서 허용할 규모는 아직 정하지 않았다. 워커 강제 중단 시험은 분리 환경에서만 한다.

## ① 여러 팀이 원본을 동시에 올림

각 방의 대표자가 원본 업로드 버튼을 거의 동시에 누른다. **업로드 완료까지**와 **YOLO 분석 완료까지**를 따로 잰다. 검출 작업의 대기 개수가 늘었다가 모두 0으로 돌아오는지 확인한다.

### Mac 요약 화면 사용

프로젝트 폴더에서 다음 명령을 실행한 뒤 Mac 브라우저에서 `http://127.0.0.1:4317`을 연다. 이 화면은 Mac의 `localhost`에만 열리며 네이티브 앱 설치가 아니다. Supabase 비밀 키는 Mac 프로세스에만 둔다.

```sh
node --env-file=.env.local --import tsx scripts/festival-watch.ts
```

1. `BTEST`처럼 실제 이름과 겹치지 않는 시험 접두어와 목표 팀 수를 고르고 **기록 시작**을 누른다.
2. 각 대표자는 `/sessions/new?festivalTest=BTEST`로 들어가 이름을 `BTEST-01`, `BTEST-02`처럼 정한다. 각기 다른 방을 만들고 원본을 거의 동시에 올린다.
3. 요약 화면에서 원본 접수·YOLO 완료·대기·실패, p95 시간과 팀별 진행을 본다. 각 브라우저의 **시험 기록 내려받기**로 받은 JSON을 요약 화면에 가져오면 Storage 전송 시간과 서버 완료 확인 시간을 나눠 볼 수 있다.
4. 시험 전후 Vercel·Supabase Usage 값을 화면 아래에 입력하고 **기록 종료·저장**을 누른다. 보고서는 Git에 포함되지 않는 `private/festival-watch/`에 저장된다. 브라우저의 **종료** 버튼은 브라우저에 남은 시험 기록을 지운다.

DB 관찰 간격은 2초여서 YOLO 시작·대기 시간에 그 정도 오차가 있다. 워커 로그의 단계별 시간은 새 계측 코드로 Mac 워커를 갱신한 경우에만 나타난다. 현재 설치 워커와 공개 앱에는 로컬 측정 코드가 아직 반영되지 않았으므로, 브라우저 JSON 내보내기와 워커 단계별 수치는 배포·설치 전에는 비어 있다. 제공업체 Usage는 다른 트래픽과 갱신 지연이 섞일 수 있어 시험 단독 청구액이 아니다.

## ② 여러 사람이 보정본을 동시에 올림

원본 분석이 끝난 방에서 참여자 3명이 보정본을 거의 동시에 올리고 영역을 제출한다. 보정본과 마스크의 **업로드·검증·제출 완료 시간**, 429 오류와 재시도 후 성공 여부를 본다. 이 흐름의 보정본 업로드 자체는 워커 YOLO 대기열에 작업을 추가하지 않는다.

## ③ 여러 팀이 동시에 병합을 요청함

서로 다른 방에서 한 명 이상 제출을 마친 뒤, 각 방 대표자가 동시에 `사진 합치기`를 누른다. **요청부터 결과 표시까지**와 병합 작업의 대기 개수를 잰다. 모든 결과가 나타나는지 확인한다.

## ④ 원본 분석과 병합이 함께 몰림

일부 새 방은 원본을 올리고, 이미 제출을 마친 다른 방은 동시에 병합을 요청한다. 두 종류의 작업이 같은 워커 대기열을 쓰므로, **각각의 대기 시간**을 ①·③의 단독 시험과 비교한다.

## ⑤ 처리 중 워커가 중단됐다가 돌아옴

분리 시험 환경에서 분석 또는 병합이 `처리 중`일 때 워커를 중지하고 다시 시작한다. 할당 만료 뒤 작업이 재할당되는지, 이미 끝난 작업이 중복 게시되지 않는지, 뒤에 쌓인 작업까지 완료되는지 확인한다. **중단 시간·복구 시간·추가 대기 시간**을 적는다.

## 측정 준비와 기록

①의 Mac 요약 화면은 DB 작업 상태를 읽어 기록하고, 시험 모드 브라우저의 업로드 시간 파일과 새 워커 로그를 합친다. 나머지 시험의 구간별 계측은 각 시험을 진행할 때 확장한다. 화면 시간만으로는 서버 대기 시간과 처리 시간을 분리할 수 없다.

| 구분 | 기록할 값 |
|---|---|
| 대기열 | 작업 종류, 접수·시작·완료 시각, 상태, 재시도 횟수, 시점별 대기 개수 |
| 워커 | YOLO·합성·파일 다운로드·결과 업로드 시간, 실패·재할당 수 |
| 서버 부하 | API 경로별 요청 수·오류/429 수·응답 시간, Vercel 함수 호출·CPU 사용량 |
| 저장·전송 | 원본·보정본·마스크·결과 바이트, 결과 다운로드 횟수, Supabase Storage·egress 사용량 |

시험별로 팀 수, 사진 크기, 시작·종료 시각, 완료/실패 수, 완료 시간의 95백분위값, 시험 전후 제공업체 Usage 차이를 기록한다. 적은 팀 수의 95백분위값은 참고값으로만 보고, 병합 5분 목표와 복구되지 않은 실패 0건은 반복 시험으로 판단한다. 무료 요금제에서도 한도 사용은 비용 판단에 포함한다. 사진·이름·초대 링크·비밀 키는 기록하지 않는다. 실제 측정값과 판단은 [STATE](../STATE.md)에 요약한다.
